# 前端开发规范 V7.0｜任务驱动版

> 适用范围：
> 基于现有前端代码继续开发《设计流转自动化管理系统》新版后台。
> 本规范用于替换旧版“以设计审核为主线”的表达，重构为“任务为核心、三类任务分型、仓库为主线节点、设计/审核为条件子流程”的前端开发规范。
> 技术栈保持不变：Vue 3 + TypeScript + Pinia + Tailwind + Vite。

## 0. 规范目标

前端不是做页面拼装，而是承担三件事：

1. 把任务主线表达清楚：任何页面都必须围绕任务展开，而不是围绕设计稿或审核单独展开。
2. 把流程责任边界表达清楚：原品开发、新品开发、采购任务三类路径必须在 UI 层清晰分流。
3. 给后续模块化扩展留接口：导出、人事 KPI、财务、API 开放、权限层级都必须从一开始预留结构，避免后续推翻重写。

## 1. 第一性原理：前端的唯一主对象

### 1.1 主对象必须是 Task（任务 / 工单）
前端所有页面、路由、列表、详情、动作入口，都必须以 task 为核心对象。
禁止再以“设计稿”“审核单”“仓库单”作为页面一级中心对象。

### 1.2 三类任务必须成为一级业务模型
前端必须内建并统一使用以下任务类型枚举：

- ORIGINAL_PRODUCT_DEV：原品开发
- NEW_PRODUCT_DEV：新品开发
- PURCHASE_TASK：采购任务

### 1.3 主线与子流程必须分层表达
前端必须把流程拆为：

#### 主线
- 创建任务
- 自动生成编码
- 入 ERP / 建档
- 维护商品基本信息
- 仓库节点
- 条件结单

#### 条件子流程
- 设计
- 审核
- 外包
- 采购处理
- 生产处理
- 财务统计
- KPI 输出

禁止继续用旧思路把所有任务都画成：
运营 -> 设计 -> 审核 -> 仓库

因为采购任务不经过设计与审核；新品任务也不允许把资料维护责任推给仓库。

## 2. 技术栈与工程边界

### 2.1 技术栈固定
- Vue 3（Composition API）
- TypeScript（strict）
- Pinia
- Tailwind CSS
- Vite

### 2.2 必须继承旧版工程边界
- 页面层只做编排
- store 收口状态
- services 收口 API
- domain 收口枚举、类型、映射
- RBAC 必须前后端协同
- 危险动作必须二次确认
- 所有模块必须具备可扩展接口意识

### 2.3 明确禁止
- 禁止在组件里硬编码任务状态、任务类型、角色文案
- 禁止页面直接拼业务状态机
- 禁止把“导出”“财务”“KPI”“权限”做成后补临时页面
- 禁止仓库页面承担新品资料补录主责任
- 禁止让 UI 逻辑默认为“所有任务都有设计图”

## 4. 页面架构重构规则

### 4.1 一级菜单必须重构
新版前端主导航建议调整为：
- Dashboard
- 任务中心
- 创建任务
- 设计工作台
- 审核工作台
- 仓库中心
- 采购中心
- 导出中心
- 财务看板（预留）
- 组织与权限
- 系统管理

### 4.2 任务中心必须成为首页级核心
任务中心必须成为全系统主入口。
至少支持：
- 按任务类型筛选
- 按任务主状态筛选
- 按设计子状态筛选
- 按仓库状态筛选
- 按负责人/部门/组长筛选
- 按是否缺图/缺成本/缺资料筛选
- 按是否可结单筛选

### 4.3 任务详情页必须成为总装配页
任务详情页必须分为 6 个信息域：
1. 任务基础信息
2. 商品与编码信息
3. 成本与价格信息
4. 设计与资产信息
5. 审核与外包信息
6. 仓库与结单信息

## 6. 三类任务的前端规则

### 6.1 原品开发
- 来自 ERP 既有产品
- 自动带出历史 SKU / 分类 / 历史资料
- 可查看历史设计版本
- 当前任务以“修改旧品”为核心

前端要求：
- 创建页支持 ERP 产品选择器
- 详情页支持历史版本/历史任务快速入口
- 默认展示“本次改动点”区域
- 仓库页能区分“原品延用资料”和“本次新增资料”

### 6.2 新品开发
必须解决：
- 运营贴链接、截图、文案
- 设计出图慢、资料补不全
- 仓库最后被迫补资料

前端必须做强门禁：
- 创建页分区录入：外部链接 / 截图 / 文案 / 初步规格
- 在任务详情中突出“资料完整度”
- 对未补齐必要字段的新品任务，必须显示红区提醒
- 仓库接收前必须清晰提示缺失项，而不是让仓库自己找图

### 6.3 采购任务
- 默认隐藏设计/审核模块
- 强化采购价 / 成本价 / 仓库必要字段
- 采购与仓库属于一个部门，可在 UI 上合并为同一处理面板
- 采购任务允许无图状态
- 采购任务可直接进入仓库节点并参与结单判断

## 7. 成本价预填规则（必须预留）

### 7.1 必须独立出“成本预估能力”
前端必须预留：
- 产品尺寸输入
- 面积计算结果展示
- 单位面积价格规则展示
- 规则来源说明
- 预估成本价
- 手动修正成本价
- 成本价锁定状态

### 7.2 前端只做展示和门禁，不做最终业务裁决
前端可以做：
- 实时计算预览
- 展示规则来源
- 提示当前是自动预填还是手工改写

前端不能做：
- 把本地计算结果直接当最终结算依据
- 跨页面自行修改成本规则

### 7.3 成本规则接口必须预留
- GET /cost-rules
- POST /cost-preview
- POST /tasks/{id}/cost-fill
- POST /tasks/{id}/cost-confirm

## 8. 导出中心（必须预留正式模块）

### 8.1 导出中心的前端职责
- 提供导出任务发起入口
- 记录导出范围、条件、格式
- 显示导出队列、导出状态、下载入口
- 控制导出权限
- 记录导出审计

### 8.2 首批必须预留的导出类型
- 任务列表导出
- 仓库处理数据导出
- 采购任务导出
- 设计资产记录导出
- 审核记录导出
- 成本数据导出
- 财务汇总数据导出
- KPI 数据导出

## 9. KPI 与开放 API（必须预留）

### 9.1 KPI 不是后补需求，而是系统能力延伸
前端必须把以下数据视为可输出资产：
- 每人任务量
- 每人完成量
- 设计打回率
- 审核通过率
- 仓库退回率
- 平均处理时长
- 超时任务量
- 采购任务完成率

### 9.2 页面层必须预留 KPI 数据块和接口调用能力
即便首版不完全上线，也要预留：
- KPI 统计页路由
- KPI API service
- 导出能力
- 部门/组长维度筛选
- 时间区间筛选

## 10. 财务板块（必须预留）

### 10.1 财务前端必须预留这些能力
- 销售额数据汇总入口
- 成本价汇总
- 毛利估算
- 商品维度利润分析
- 时间区间趋势分析
- 任务类型维度分析
- 分类维度分析

### 10.2 财务不代表首期全做，但必须预留模块边界
必须有：
- finance/ 目录
- 财务 service
- 财务 domain type
- 财务菜单占位或权限隐藏入口
- 财务导出结构

## 11. 登录、组织、权限体系（必须重构）

### 11.1 角色必须分层
平台层：
- 超级管理员
- 系统管理员

部门层：
- 运营
- 设计
- 审核
- 仓库/采购
- 财务
- 人事
- 只读访客

管理层：
- 部门负责人
- 组长

### 11.2 权限必须至少分三层
- 路由权限
- 页面动作权限
- 数据范围权限

### 11.3 数据范围权限必须提前设计
例如：
- 只能看本组任务
- 只能看本部门任务
- 可看全部任务
- 可看自己创建的任务
- 可看自己参与的任务

## 13. Definition of Done（新版）

以下任一项没做到，都不算合格交付：

- [ ] 所有页面以任务为主对象，不再以设计稿为主对象
- [ ] 三类任务已独立建模并在 UI 区分展示
- [ ] 主状态与子状态已拆层
- [ ] 采购任务支持无图流程
- [ ] 新品任务有资料完整度门禁
- [ ] 成本价预填结构已预留
- [ ] 导出中心已预留模块与接口结构
- [ ] KPI 模块已预留接口与页面边界
- [ ] 财务模块已预留接口与页面边界
- [ ] 权限体系支持超级管理员 / 部门 / 组长 / 数据范围
- [ ] 危险动作有 reason、确认、审计
- [ ] 页面继续遵守原有 UI/工程门禁
