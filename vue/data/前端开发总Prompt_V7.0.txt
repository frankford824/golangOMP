你现在要基于“现有前端代码”继续开发，不允许推翻重写技术栈，不允许脱离现有工程边界自由发挥。

【项目背景】
这是一个任务驱动型商品流转系统，前端技术栈固定为：
- Vue 3
- TypeScript（strict）
- Pinia
- Tailwind
- Vite

你必须继承已有工程规范与分层方式：
- views 只做页面编排
- stores 收口状态
- services/api 收口接口
- domain/enums/types/mappers 收口业务模型
- 组件层不硬编码业务状态
- 权限、状态、枚举、动作必须可审计、可扩展

【这次开发的核心变化】
旧系统偏“设计审核主线”，现在必须重构为“任务为核心”的系统。

新的唯一主对象是：Task（任务 / 工单）

所有流程围绕任务展开，且任务分为三类：
1. ORIGINAL_PRODUCT_DEV 原品开发
2. NEW_PRODUCT_DEV 新品开发
3. PURCHASE_TASK 采购任务

【新的流程认知】
系统主线不是：
运营 -> 设计 -> 审核 -> 仓库

而是：
创建任务 -> 自动生成编码 -> 入 ERP/建档 -> 维护商品基本信息 -> 仓库节点 -> 条件结单

其中：
- 设计、审核、外包、采购、生产 都是围绕任务的条件子流程
- 采购任务通常不经过设计与审核
- 采购任务可无图
- 仓库是主线关键节点，不再只是末端接收方
- 新品开发不允许把资料补录责任推给仓库

【前端必须实现的核心目标】
1. 所有页面以任务为一级中心对象
2. 三类任务必须做独立 UI 分流
3. 主状态与子状态必须拆层建模
4. 任务详情页必须成为总装配页
5. 采购任务必须支持无图直达仓库路径
6. 新品任务必须做资料完整度门禁
7. 原品开发必须支持带出 ERP 历史产品与历史资料
8. 成本价预填规则必须预留独立模块能力
9. 导出中心必须预留独立模块
10. KPI、人事、财务、开放 API 必须预留模块边界
11. 登录、组织、权限、组长权限、数据范围权限必须系统设计

【成本价预填要求】
系统必须预留成本价自动预填能力，适配 KT 板、节日礼品等业务。
前端必须支持：
- 产品尺寸输入
- 面积计算结果展示
- 单位面积价格规则展示
- 自动预估成本价
- 手工修正成本价
- 当前成本来源（自动/手工）标识
前端只做展示和门禁，不直接作为最终财务结算依据。

【必须预留的模块】
- 导出中心
- KPI 统计
- 财务看板
- 权限与组织管理
- API 对接能力
- 审计日志展示能力

至少重构/实现以下模块：

【任务详情页必须拆为以下区域】
1. 任务基础信息
2. 商品与编码信息
3. 成本与价格信息
4. 设计与资产信息
5. 审核与外包信息
6. 仓库与结单信息

【状态模型要求】
你必须显式建模：
- 任务主状态
- 设计子状态
- 审核子状态
- 仓库子状态
- 采购子状态
- 结单状态

禁止在组件中写散落的字符串判断。

【权限要求】
必须支持：
- 超级管理员
- 系统管理员
- 部门角色
- 部门负责人
- 组长
- 普通成员
- 数据范围权限（本人/本组/本部门/全部）

【开发原则】
1. 只允许在现有代码结构上演进，不推翻重建
2. 优先复用已有组件、store、service、路由结构
3. 先抽象 domain enums/types，再改页面
4. 先完成任务模型，再改各子模块
5. 所有新增功能都必须考虑后续导出、KPI、财务、API 扩展
6. 所有关键动作要预留 reason、审计、权限控制
7. 不要把采购任务硬套进设计流程
8. 不要让仓库承担新品资料补录主责任
9. 所有页面必须继续符合原有 UI 门禁：
   - 禁 emoji
   - 移动端禁用 h-screen，使用 min-h-[100dvh]
   - 优先 grid 布局
   - 动画只允许 transform/opacity
   - 所有异步状态必须有 loading/empty/error
10. 任何不确定的字段或接口，优先预留扩展点，不要临时写死
